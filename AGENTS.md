- For mapping, proposing, adding, changing, or removing player states or their transition wiring, use the repository-local [player-state-workflow skill](.agents/skills/player-state-workflow/SKILL.md). Generate the current flow from source, show before/proposed-after diagrams and transition/test ramifications before gameplay edits, and compare the actual result afterward. The preview is not an additional permission gate when implementation is already authorized. Start with the [generated current flow](Assets/Docs/PlayerStateFlow/current.md), then regenerate it rather than trusting a stale snapshot.
- STATE-001 policies are agreed (2026-10-17); STATE-002 characterization and ENG-006 integration have 2026-10-18 evidence. NET-001 retains the remaining network validation matrix. The matrix exists in `Assets/Docs/PLAYER_STATE_REVIEW.md`; review it and the rulebook's reviewed application policies before implementing state changes. The reviewed profile uses Immediate placement by default, optional match-fixed Draft/undo, manual one-tile announcements/opponent challenges, default DrawOneTile penalty, readiness sets, joint winners and suspension. Follow R-015–R-018; additional app policies still need review.
- Keep known implementation behavior, intended rules, and proposals distinct. Do not assume generic train-dominoes rules apply without checking the agreed variant.
- Keep the server authoritative. UI button availability is not rule validation; validate acting player, action legality, and repeated/stale commands at the authoritative boundary.
- Follow the rules-engine plan's source-based assembly boundary and external test project using the same core sources. Targets are .NET Standard 2.1 / supported C# 9 for core and .NET 10 / NUnit for external tests. The shared-source projects/harness now exist under RulesEngine; run commands from that directory to enforce its SDK pin. Avoid manually copied DLLs and duplicated rule implementations.
- Keep Unity, Netcode, input, rendering, animation, and transport serialization outside the rules core. Make randomness controllable for reproducible tests. Extract in small tested slices, preserving IDs and payload compatibility unless migration is explicitly in scope.
- Balance state event subscriptions on entry/exit. Review group-turn, individual-turn, undo, and reset behavior together when changing shared state infrastructure.

## Unity and repository care

- Use the editor version in `ProjectSettings/ProjectVersion.txt` and installed package versions in `Packages/manifest.json`; do not upgrade packages incidentally.
- Prefer Unity's command-line interface (CLI) for repeatable editor tasks and verification, including batch-mode builds/imports, project-defined `-executeMethod` checks, and driving a running Editor when the CLI supports the task. Before relying on it, check availability with `unity version`/`unity doctor` and inspect `unity skill show` for current commands. This machine has the Unity CLI on PATH; the project editor is pinned by `ProjectSettings/ProjectVersion.txt` to `6000.6.6f1` at `/Applications/Unity/Hub/Editor/6000.6.6f1/Unity.app/Contents/MacOS/Unity`. CLI account/license access is environment-dependent: check `unity auth list` for account-dependent CLI features, and confirm the Editor license is usable for batchmode; do not assume login or license state from the executable being installed. If access is missing, report the specific blocker and use available offline/local checks. Check the relevant README for exact command scope. Reserve computer use for work that needs interactive GUI behavior, visual inspection, or a live editor/device workflow; CLI checks do not establish host/client or live-service correctness unless the harness explicitly covers it.
- Preserve asset GUIDs, `.meta` files, serialized field references, and scene/prefab wiring. Use Unity-aware moves for assets; do not regenerate metadata for existing assets.
- Avoid generated project/cache edits (`Library`, `Temp`, `Logs`, generated `.csproj`/solution files) and third-party source edits unless explicitly required by the task. Preserve unrelated user changes.
- The inspected scene enables `IgnoreDominoComparisons` and starts at round 2. Recheck settings before verification; development bypasses are not intended rules. Do not silently change saved settings merely to make a test pass.
- For new grouped domino animations, explicitly consider bounded staggering of start times and/or arrivals instead of making every tile move identically. Follow [animation guidelines](Assets/Docs/ANIMATION_GUIDELINES.md): preserve existing assets, validate projected separation under independent phases, keep one transform owner, support reduced motion, and never make animation completion authoritative.
- Final four-color domino asset integration is late priority after rule/state work. Preserve the user's art and keep presentation ownership/color separate from rule decisions.
